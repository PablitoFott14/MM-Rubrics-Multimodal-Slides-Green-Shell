The 80/20 rule

12 objective criteria · 20% is 2.4 · at most 2 may grade process
Count the objective block only, positives and negatives alike, and round down. Over 20% fails the task automatically; zero process criteria is the preferred outcome.

Section 2

Your Role

You are not answering tasks. You are building the thing that grades a model.
  • You turn an assigned scenario into a single turn multimodal task that stresses tools, media and reasoning together
  • You solve it yourself first, then write the rubric set that defines what a correct answer had to deliver
  • You steer a second model to the golden: proof the task is solvable at all, and the bar presentation is judged against

Mindset

  • Do not optimise for first try success. A task the model breezes through carries no signal
  • Difficulty must come from the work, never from trivia or contrived constraints
Your rubrics become ground truth in real model evaluation. A criterion that grades something the prompt never asked for does not just lose you a task. It teaches the model the wrong thing.
Three things you hand in
1 · Objective rubric block
Written from your GTFA, rated on Model A, a justification for every failure.
2 · Golden artifacts
The same deliverable in its best form, reached by hinting Model B.
3 · Subjective rubric block
Presentation only, rated on Model A and the golden side by side.
One prompt, run on two models. Everything you hand in comes out of those two runs.

The Hard Rules

Parameters that are checked before anything else is read
  • Single turn only. Model A gets the prompt and nothing else. A second user turn in Leg A fails the task
  • Assigned parameters. All fourteen followed exactly. Deviate only where the guidelines allow, and justify it
  • Universe adherence. The assigned universe, loaded correctly, and solvable with it plus the input files, nothing else
  • Three multimodal inputs, minimum, in the Model A conversation, covering every assigned input modality
  • Realism. The scenario plausibly fits the persona, the use case and the subcategory

Turn budget
Model A gets one turn.
Model B gets what it needs.
Leg A
One prompt, sent automatically. No follow ups.
Leg B
The same prompt word for word, then as many intent level hints as it takes to reach the golden.

Client Requirements
Section 3

Genuine Complexity, Not Artificial

Depth comes from a well planned scenario, never from friction bolted on afterwards

✓  Where real difficulty comes from

  • Multi stage planning across the inputs and the universe, with real dependencies
  • Decision logic: thresholds and rules from the inputs, conditionals, reconciliation
  • Natural friction: conflicting data, missing fields, normalization issues, constraint conflicts
  • Evidence split across modalities, so no single source answers it
  • Distractors a careful model has to rule out

✗  Where it must never come from

  • Stacked constraints. Three or more formatting rules fail QC on their own
  • Contrived inputs, or media no person could read
  • Extra asks piled on with no realistic reason behind them
  • Patching the scenario after watching Model A pass
  • A missing tool or library. The agent installs what it lacks, so that is a delay, never a blocker
Long, not deep
SlackEmailCalendarDrive → every fact from one document
Four services, seven steps, one source. A long chore, not a hard task.
Deep
serial off a label→CRM record→transactions→policy rule→decision
Each step needs what the one before it found.
Where models genuinely stumble opening a connected service at alltesting a tool before calling it unavailablefinding the real value instead of askingtrusting OCR over the imagetelling what is in the folder from what is in scope
Never in output formats, arithmetic on values it already holds, or conventions the prompt states: models clear those. Grade the stumble where it lands, in the deliverable.
Length is not depth. Plan the layers of complexity before the first run and know where Model A should fail. Patching the scenario halfway through never replaces proper design.

Section 5

Adherence, And When You May Deviate

Fill in what the scenario leaves open. Change nothing it settles.

How QC reads your scenario

5
Followed closely. Same user, goal and deliverable. Only the details the scenario leaves open were filled in
3
Loose. One element changed beyond filling gaps, such as a different deliverable type or a goal the scenario never implies
2
Not followed, a fail. The user, the goal or the deliverable changed, or the scenario shrank to a passing mention
The universe, the input modalities and the output artifact are each checked against the sheet the same way.

Deviation is the exception

Only two circumstances allow it:
1 · Universe limitation
The resource is genuinely missing from the assigned universe: Google Drive is an assigned tool, and no Google Drive server exists.
2 · Insufficient complexity
The assigned setup cannot produce the minimum genuine failure, so complexity rises while every other parameter holds.
Either way: only what is strictly necessary, the scenario's intent intact, and a clear justification.
Universe misadherence must never come from insufficient exploration. A drift justified by “the universe could not support it”, when review shows it could, fails the task automatically.

Section 6

Check It, Never Assume It

Static dates and unverified capabilities are the two quiet ways a task breaks

⚠  Dates are static

  • Universe calendars hold fixed dates and do not move with the day the task is run, so “next Tuesday” can land on a week that holds nothing
  • Anchor to a range you have actually seen, and write that date into the prompt: “the week of 12 May”, not “next Tuesday”
  • Pinned in the prompt, the window is the same for Model A, Model B and the reviewer
BAD   Can you check what I have on next Tuesday?
GOOD  Can you check what I have on Tuesday 12 May?

?  Not sure it is possible

  • Ask the AI agent directly. It tells you what it can reach and what it cannot, faster than guessing from the outside
  • Open Agent tool access. It lists every tool each server exposes. A server with few tools is not a weak server
  • Your assigned tools define the task. The wider loadout is background, never a reason to build on a different service

Every fact the model needs must be reachable in the prompt, the input files or the universe. If it is reachable nowhere, the task is unsolvable and no rubric written against it can be defended.

At least three in the Model A conversation. Three is the floor, not the target.
  • Start from your assigned input modalities. Use every one listed, each carrying part of the answer

Section 6 · Building the Idea
Multimodal Inputs
Section 6

Universe And Multimodal Context Together

Each required input carries a distinct part of the answer, and no single one is enough

✓  What that looks like

Strong reconciliation with the universe is expected in almost every scenario.
  • A value read off an image is what lets the model find the matching record in the universe
  • The universe supplies what the media cannot: earlier messages, contacts, transaction history, the state of a folder
  • The model has to read the universe, not only write to it, with the assigned tools coordinating toward one goal
label photo: the only serial→CRM record→transaction history→reconciled
A product label in a photo carries the only visible serial number. The model uses it to find the matching record in the universe CRM, then reconciles it with the related transaction history.

✗  Four ways it goes wrong

  • Write only. Every figure comes from the attachments, and the universe only receives notes, events and drafts
  • Universe dropped. The media settles everything, and nothing is reconciled against what the universe holds
  • Pictures of the universe. An input with no natural reason to exist, or one that duplicates what the universe already holds
  • A cross check nobody could perform. The reconciliation hangs on an input no person could read, so the failure is the task's, not the model's
The ablation test. Take the attachments away. If the task still lands, the media is decorative and the task goes back. A transcript sitting next to the audio it transcribes fails the same way: the model never has to listen.

Ground Truth Final Answer: the complete expected end state, written before anything runs
Once the logic holds, solve the task yourself and write the answer down: every deliverable, every value it must contain, and the reasoning that resolves each edge case.
It makes the Desired Outcome verifiable
You cannot define an end state you have not worked out.
It turns review into verification
Model A is compared against an answer already settled, so subtle misses show.
It gives the rubrics their substance
Each criterion comes from a fact you resolved: a total, a date, a classification.

Where the settled scenario is formalised, before anything runs
Four fields, completed in order. They put the rubrics, the golden and the reviewer on one source of truth.

Agent Objective

Who the user is, the problem, the context, and the artifacts they need at the end. Why the agent exists, never the steps.

Section 10

Valid vs Invalid Failures

Before you write a rubric for a miss, ask one question: did the model have a fair opportunity to get it right?

✓  Valid: a decision the model made

  • Misread a legible value. A figure any person could read off the file came through wrong, and the error carried into the artifact
  • Filename taken as evidence. A claim made without the file ever being opened. Still valid if the file would have supported it, because the claim was never grounded
  • Universe evidence never found. The record was there and reachable, and the model answered without it
  • Cross reference collapsed to one side. Asked to reconcile the media against the universe, it trusted one of them
  • Logic flow misapplied. The prompt and the media each carry part of the rule, and a step was dropped or applied out of order
  • An accessible tool left unused. The server is loaded and the model estimates instead of querying it
  • Conditional handled wrong. An optional session counted anyway, or a branch tripped that the ground truth never trips
  • Fabricated precision. Measurements stated to the millimetre with no ruler in frame

✗  Not valid: your defect, or the platform's

  • The run broke. prompt-error, idle timeout, session abort, trajectory execution error. The model never got to decide anything
  • A forbidden input format. A .heic file that crashes or times out the run is your defect
  • A requirement the model never saw. A rubric demanding a heading that appears only in the Desired Outcome
  • Media no person could read either. Illegible handwriting, a photo too dark or too blurred
  • An undecided source conflict. The prompt never said which source wins, so either answer was defensible
  • Contradictory multimodal input. The file carries an instruction or evidence that rewrites the task
  • Contrived scenario. Verbosity and extra asks piled on, with no realistic background behind them
  • Data that is not in the server, asked for anyway, and the model penalised for not finding it
Never turn an invalid failure into failing rubrics, and never count it toward the 30%. Fix the task instead.

Section 11

The 80/20 Rule

Grade what the agent delivered. How it got there is secondary, and capped.
Completion · at least 80%
Process · 20% max

Completion: what was delivered

The required artifact, the instructions followed, the outcome the user asked for. A reasoning decision is graded where it lands: the value, classification or decision written into the deliverable.
Task Completion and Instruction Following on Final Answer Artifact, State Change or User-Facing Message. Safety criteria that grade the final state.

Process: how it got there

Tool use, step order, what it inspected, narration of its own work. Kept only when no deliverable can show the failure, such as a live value the model could fake without calling the tool. Zero is preferred.
Tool Use, Agent Behavior, any Trajectory target, final messages narrating the process, Safety criteria about asking before acting.
The test
Could the deliverable be perfect and this criterion still fail? Then it is process. Rewrite it as completion whenever you can.
How to count
Objective block only, positives and negatives alike, rounded down: 12 criteria allow 2, since 20% of 12 is 2.4. Over the cap fails automatically.
✗ PROCESS     The model opens klin.png before writing report.md.
✓ COMPLETION  report.md records the 48 spaces per rack shown in klin.png.

Category, Target, Weight

Every criterion carries all three. They shape how the client reads the data, so none of them is a formality.

Evaluation target · where the grader looks

Final Answer Artifact. Content of files the agent created or modified, never mere existence
State Change. A record created, updated or deleted, read from snapshots.json
User-Facing Message. What the agent actually told the user in chat
Trajectory. The reasoning path. Every one counts toward the 20% cap

Category · the question that decides it

Task Completion. The default. Could the model simply be wrong at it?
Instruction Following. Only knowable by being told: formats, filenames, limits
Safety & Boundaries. Only when irreversible harm or a data leak is the point
Tool Use. Only when the model could fake the answer without the tool. Capped
Agent Behavior. Trajectory only, and the exception. Capped

Weight is difficulty, never importance

 How hard to satisfy How tempting to get wrong
+5Three or more axes−5The setup pulls the model into it
+3Exactly two axes−3A plausible wrong default
+1Zero or one: mechanical−1Rare, out of character

The four difficulty axes

Coordination. Three or more sources reconciled, or tools chained
Reasoning depth. Multi step inference, conditionals, calculation
Modality. Cross modal work across image, data and text
Discovery. SQL queries, hidden fields, cross document tracing

Section 11

Building the Block

Coverage, negatives, repeated outcomes, and the justification every failure needs

Composition

  • No fixed count. Coverage decides it, often 15 to 30 criteria
  • Positives are the default, even for a prohibition: define the correct outcome and the “do not” is covered
  • Negatives around 25%, below 30%, each naming a failure the setup genuinely invites
  • Before adding one, ask: could a positive cover it? Did the model do it? Would anything go ungraded without it? Two noes make it redundant

Repeated outcomes · more than 8

One completeness criterion, plus up to five spot checks on the strongest signal cases.
✓ A cancellation receipt is produced for all
  9 confirmed vendors.
✓ The Northgate Hosting receipt records $2,340.00,
  from the invoice image, not the stale tracker.
✗ Nine criteria, one per vendor.
OR logic only between equally valid outcomes the scenario leaves open, never to hedge.

The three parts of a failure justification

Every positive rated Not Present and every negative rated Present on Model A. Rate with the trajectory, the final artifacts and the GTFA open, and check any pre filled selection rather than trusting it.
1 · Why the rubric is correct
Quote the prompt or input policy. “The prompt states: create a reminder only if a cardiology follow up exists within the next month.”
2 · Where Model A failed
The exact turn, tool call or output. “Calls 14 and 18 search the wrong date range, and the reminder is still created at tool 27.”
3 · Why it is necessary
What it costs a correct answer. “The user set the range; respecting it is what grounds the lookup and avoids an unsupported state change.”
Definitive, never “it checks an important thing”. If you cannot write all three, delete the rubric. The golden needs none.

Section 12

Hinting Without Leaking

Say that something is wrong, or where to look. Never what the answer is.
✓ A hint may
Say that something is still missing or wrong · point at the area to revisit: “the photos I sent”, “our project channel” · stay oblique enough to need reasoning: “A is wrong” · steer toward a requirement the prompt already makes
✗ A hint may never
Hand over a value, count, position or conclusion the model should derive, a leak that fails the task · say “A is wrong, do B instead” · add a requirement the prompt never made · name the exact file to open, over steering that is marked down
Worked: workout_tracker.html should hold one entry per session that actually happened between 3 February and 26 April, naming the exercises done and embedding that session's media.

Section 12 · Golden Solution
Hinting
Section 12

What Makes It Golden

The bar the artifact has to clear, and what to do when it will not come

✓  The golden is

  • The same deliverable in its best form, not a different or a larger one
  • Every file the prompt named, spelled verbatim, with every content rule satisfied
  • Grounded in the actual inputs: images opened, videos watched, PDFs read. Nothing asserted from a filename
  • Artifacts only. Narrating how it was reached is a defect

✗  The golden is not

  • A bigger deliverable. Sections nobody asked for make it a different task, not a better answer
  • A rewritten prompt. If getting there needs the prompt changed, the prompt is what is wrong
  • A lucky run. Reaching it once by accident proves nothing. You have to be able to steer it there

When the golden will not come

The scenario is genuine and feasible
Keep steering with hints until the model reaches the target. Hinting is the only valid path: switching approaches is an automatic rejection.
The setup is contrived or infeasible
Stop hinting and fix the task: rework the inputs and the prompt inside the assigned scenario, then restart from Leg A, since both legs run the same prompt.
This leg is what makes the failure bar coherent. Model A misses at least 30% while the same prompt, universe and inputs come out right here. If you cannot reach the ideal response yourself, the scenario was never solvable, and the thing to fix is the task, not the model.
