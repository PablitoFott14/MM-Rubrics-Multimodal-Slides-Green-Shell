One prompt, two runs, three things you hand in

Planning is not optional

  • Dedicate time to meaningful planning, in depth universe exploration, and meticulous multimodal creation
  • Follow the assigned task parameters as closely as possible. Not exploring the universe enough does not automatically mean the task fails to follow its assigned parameters

Turn budget

  • Leg A: one prompt, sent automatically. The Task Runner's 8 steps get completed automatically
  • Leg B: the same prompt word for word, then as many intent level hints as it takes to reach the prompt's golden solution (passing every positive rubric)
Do not optimize for first try success. A task the model breezes through carries no signal, and the difficulty has to come from the work, never from trivia or contrived constraints.

Section 2

Genuine Complexity

Planned in from the start, never patched in after the run

Three dependent stages, in one turn

1 · ACQUIRE
Gather relevant evidence from the universe, ensure alignment with assigned task parameters, and identify realistic opportunities to increase complexity. Brainstorm yourself
→
2 · REASON
Reconcile information, perform calculations, resolve contradictions, and apply the rules and constraints relevant to the task
→
3 · PRODUCE
Build meaningful multimodal inputs, define the scenario's requirements, identify genuine areas where the model may fail, and finalize a coherent, well planned task
Each stage needs the one before it, across several systems. If a short linear exchange could finish the task, it is too simple.

✓  Real difficulty

  • Evidence split across modalities and services
  • Decision logic the inputs carry: thresholds, conditionals
  • Natural friction: conflicting records, missing fields
  • Distractors a careful model has to rule out

✗  Never from

  • Stacked rules without any realistic purpose
  • Contrived or unreadable inputs
  • Extra asks with no realistic reason just to meet any task parameter
  • Patching the scenario after Model A passes

The floor for each deliverable

The main one must be what the task parameters say.
Explainer videoSeveral scenes driven by the task's data. Not one static frame with narrationP0
Interactive HTMLControls that respond and state that changes. Not a styled static pageP0
DashboardSeveral linked views over data the model extracted. One chart is not a dashboardP0
Presentation10 to 15 slides minimum, carrying a structured narrativeP1
Designed PDFMulti page, with a designed layout. Not a text dumpP1
CSV or dataMulti row, derived from the media, in the schema its platform expectsP1
Document or reportProfessional register: sections, tables, figures the text refers toP2
Not acceptable Single step workflowsSimple summariesBasic searchesStatic reasoning, no toolsImpossible with the tools
Plan for at least two hours before the task is ready: parameters, universe, inputs, layers of complexity, and a GTFA that shows where Model A should fail. No improvising, no mid course fixes.

Your Task Parameters

Fourteen assigned parameters. All planning starts here, and every row is binding.
ParameterWhat it binds you to
Task TypeAlways single turn: the prompt and no follow ups
Use Case (L1)One of 11. Read it by intent: what the user is trying to get done
Subcategory (L2)One of 68. Stay inside it: a neighbor that fits better is a relevance failure
UniverseLoad it correctly and explore it before drafting anything
ScenarioKeep its user, goal and deliverable. Fill in only what it leaves open
Assigned toolsThe correct final state depends on them, not on the easiest service
Output artifactClears its complexity floor, and the prompt names the file
Primary capabilityThe core workflow and the deliverable exercise it
Secondary capabilitiesEach one shapes the workflow and the result, not just the wording
Input modalitiesEvery listed modality is used, each carrying part of the answer
Output modalitiesThe deliverable stays within them: audio when only text is listed is drift
Execution targetWhere the deliverable ends up and any limit, both stated in the prompt
Verification conditionThe minimum your GTFA and rubrics cover. Never revealed in the prompt
Access the scenario assumesThe agent retrieves that data itself. Read scope means no writes
Deviation is the exception
Only two reasons allow it:
1 · Universe limitation
The resource is genuinely missing: Google Drive is assigned and no Drive server exists
2 · Insufficient complexity
The setup cannot reach the 30% failure bar, so complexity rises while every other parameter holds
Either way: only what is strictly necessary, the scenario's intent intact, and a clear justification.
Omitting, substituting or drifting from any parameter makes the task invalid and subject to automatic rejection.

Section 3

Start With The Universe

The loadout decides what the task can be. Explore it before you draft anything.
  • Load it correctly. Paste the assigned Service Universe Artifact ID into the Universe Creator. The field says optional; here it is not
  • Confirm what loaded. Only a few servers in the Universe Explorer means a bad load: an environment defect, never a model failure. Reload before going on
  • Explore for real. Ask the in universe agent, query with SQL, check Agent tool access. Undocumented does not mean infeasible
  • Download it whole. Database tab, then Export SQL dump
  • Pin the dates. Universe dates are static, so write the real one into the prompt: “Tuesday 12 May”, never “next Tuesday”
  • Check every fact is reachable in the prompt, the inputs or the universe. Reachable nowhere means unsolvable
Drifting because “the universe could not support it”, when review shows it could, fails the task automatically.

Section 3

Solve It First: GTFA And Draft History

Settle the answer, then write the scenario down. Both before anything runs.

GTFA · Ground Truth Final Answer

The complete expected end state, solved by you: every deliverable, every value, and the reasoning behind each edge case.
GTFA · brake_dispute.html
14 Mar  $412.60  Greenway Motors, second payment
  → duplicate. Twice in FinTrack, once on the invoice photo
Rear brake pads  $96.40
  → dispute. Voice note: never replaced
Bank rules (email, 2 Feb): 60 day window → both qualify
Execution → nothing sent to the bank or the garage
↓ BECOMES A CRITERION
“brake_dispute.html flags the second $412.60 Greenway Motors payment of 14 March as a duplicate, because the invoice photo records a single payment.”
Task CompletionFinal Answer Artifact+5
Unsure which answer is right? Then the GTFA is not settled, and OR rubrics will not fix it.

Draft History · four fields, in order

1 · Agent Objective *
Who the user is, the problem, the context and the artifacts they need. Why the agent exists, never the steps
2 · Desired Outcome *
The end state: each artifact named, what it must contain, and the decision logic behind it
3 · Category and Subcategory *
Assigned with the task. Confirm the scenario, inputs and prompt stay inside the pair
4 · Zip Folder Upload *
Every file the prompt refers to, including at least 3 multimodal inputs
The agent never sees the Draft History. The prompt and the inputs are its only context, so a rule that lives only in the Desired Outcome cannot be graded.

The Prompt

One turn carries the whole request. There is no second message to fix it.
USER · THE ONLY TURN
Greenway Motors did my brakes in March and I'm fairly sure they charged me twice. 1 From the mechanic's voice note I also think I paid for parts they never fitted. The invoice photo, the voice note and a photo of the old parts they handed back are all in the folder. 2 Go through my March card payments, 3 hold them up against the dispute rules my bank emailed me, 4 and build brake_dispute.html: every charge I should dispute, what it should have been and the evidence for each, with a way to tick them off as I check them. 5 Don't contact the bank or the garage, I want to read it first. 6
1A real goal, in the user's own voice
4The rules live in a source the agent has to find
2Inputs pointed at the way a person would, without saying what is in them
5One named deliverable: what it holds and how it responds. No visual spec
3The universe has to be read, inside a pinned window
6The execution target: nothing sent
Never in the prompt
✗ The Verification condition's answers
✗ Thresholds and rules the inputs can carry

✗ A numbered pipeline of steps or tool calls

The failure bar

Model A rubric score
preferredacceptedtrivial task
0%50%70%100%
  • Genuine failures worth at least 30% of the final rubric score, 50% or more preferred
  • A Model A score above 70% fails as a trivial task
  • Below the bar? Back to planning, then rerun. Never pad or misrate the rubrics

Section 5

Objective Rubrics

Binary criteria about what Model A delivered, written from your GTFA
Completion · at least 80%
Process · 20% max
The artifact, the state change, the final messageTool use, trajectory, narration · zero preferred
The test
Could the deliverable be perfect and this criterion still fail? Then it is process. Rewrite it as completion.
✗ PROCESS     The model opens klin.png before writing report.md.
✓ COMPLETION  report.md records the 48 spaces per rack shown
              in klin.png.
How to count
Objective block only, positives and negatives alike, rounded down.
12 criteria · 20% is 2.4 · at most 2 may grade process
Over the cap fails the task automatically.

Every criterion is

Atomic. One grading signal, tied to one intent
Self contained. Ratable from the criterion and its target alone
Positively phrased. The signed weight carries the polarity
Literal. Every filename, ID, value and date copied from the source
Never existence. Content implies it. An existence check fails the task
Intent focused. Only what the prompt and the scenario require
Category Task Completion · the defaultInstruction FollowingSafety & BoundariesTool UseAgent Behavior
Target Final Answer ArtifactState ChangeUser-Facing MessageTrajectory
Tool Use, Agent Behavior and every Trajectory target count as process. Rate each criterion Present or Not Present on Model A.

Section 5

Weight, Coverage, Justification

Weight is difficulty, never importance

The weight set

 How hard to satisfy How tempting to get wrong
+5Three or more axes−5The setup pulls the model into it
+3Exactly two axes−3A plausible wrong default
+1Zero or one: mechanical. Format checks stay here−1Rare, out of character
Only −5 −3 −1 +1 +3 +5 are valid.

The four difficulty axes

Coordination. Three or more sources reconciled, or tools chained
Reasoning depth. Multi step inference, conditionals, calculation
Modality. Cross modal work across image, data and text
Discovery. SQL queries, hidden fields, cross document tracing
“brake_dispute.html flags the second $412.60 payment as a duplicate, because the invoice photo records a single payment.”
✓ Modality✓ Discovery✓ Reasoning→+5

Cover everything

No fixed count, often 15 to 30. Every ask in the prompt gets a criterion. Negatives around 25%, below 30%, each one a failure the setup invites.

Spot check repeats

More than 8 similar outcomes: one completeness criterion plus up to five spot checks on the strongest cases. OR only between equally valid outcomes, never to hedge.

Justify every failure

1 · Why the rubric is correct, quoting the prompt
2 · Where Model A failed: the exact call or output
3 · Why it is necessary
The golden needs none.
Issues are counted against the size of your block: major above 10%, moderate above 15%, minor above 20% fails the task. In practice, 2 to 4 issues are enough for a rejection.

Section 6

Leg B · The Golden

Same prompt, word for word, on a different model. Hint until the response is ideal.

What changes

  • A different model: GPT in Leg A, Opus here
  • Hinting is the method, not an optional step
  • No turn cap. Nudges and a cleanup turn are fine at intent level

What stays exactly the same

  • The workflow, the universe and the prompt, word for word
  • The intent and the persona, first message to last
  • The no leak rule, and the Preferred star
✓  Hint: what is still missing, from the user's side✗  Leak: the answer, or exactly where it is
“I still cannot see anything from the studio walkthrough reflected in the audit.”“Add the corrected price to the audit.”
“I think that list is still missing some elements that may be relevant for the report.”“There should be four of them.”
“I remember sharing some relevant updates in our project channel.”“Go to the OpenClaw Slack channel and get the updates sent in December.”
✓ The golden is
The same deliverable in its best form · every file named exactly as requested · grounded in the actual inputs · artifacts only
✗ The golden is not
A bigger deliverable · a rewritten prompt · a lucky run you could not steer to again
Still wrong on a feasible scenario? Keep hinting: switching approaches is an automatic rejection. A contrived or infeasible setup? Fix the task and restart from Leg A.
